# 밥플래너 MVP 현황

무엇이 실제로 되고, 무엇이 개발용 값으로 돌아가고, 무엇이 데이터가 없어서
막혀 있고, 무엇이 운영 전에 남았는지를 나눠 적는다.

이 구분이 이 문서의 전부다. 네 가지를 섞어 놓으면 "AI 기능 완성"처럼 읽히고,
그건 사실이 아니다.

---

## 1. 완료된 것

실제로 동작하고 테스트로 고정돼 있다.

### 인증과 권한
- 휴대폰 인증 → 회원가입 → 로그인 → 토큰 갱신 → 로그아웃
- BCrypt 비밀번호, refresh token 회전, 세션 저장
- 네 종류의 접근 주체: 익명 / USER / ADMIN / INTERNAL_SERVICE
- 일반 가입으로 ADMIN을 만들 수 없다. 권한 승격 API도 없다

### 사용자 기능
- 식단 조회(날짜·식사·분류·식당 필터), 상세, 영양정보, 알레르기
- 현재 혼잡도
- 잔반 인증: 이미지 업로드 → 비동기 분석 → 결과 폴링
- 리워드 저장과 조회
- 공지, 만족도 조사 응답, 문의/건의

### 관리자 기능
- 식단 CRUD, 공지 CRUD, 설문 등록·결과, 문의 답변
- 급식소 목록
- 혼잡도 시계열, 잔반 요약·메뉴별 잔반률
- 예상 식수 실행·이력, 발주 추천 실행·조회
- 관리자 웹(React) 전 화면

### 경계와 저장
- Spring ↔ FastAPI 프로세스 경계 3개(잔반·수요·발주)
- 혼잡도 수집 경로: 이력과 현재값을 한 트랜잭션에서 기록
- MySQL 8.4 + Flyway V1~V25
- 급식 운영일 시간대를 설정으로 분리

---

## 2. 개발용 fixture로 도는 것

**아래 둘은 실제 모델이 아니다.** 프로세스 경계와 계약이 연결됐는지 확인하는
용도다.

| 기능 | `modelVersion` | 실제 동작 |
|---|---|---|
| 수요 예측 | `fastapi-fixture-demand-v1` | 입력과 무관하게 항상 100명 |
| 발주 추천 | `fastapi-fixture-procurement-v1` | 계획 수량 그대로, 조정률 0 |

별도로 **식수 예측 PoC**(`/api/v1/admin/demand-forecasts/*`)가 있다. fixture가 아니라
FastAPI가 저장된 모델로 계산한 값이지만, 그 모델은 **합성데이터로 학습한 PoC**다.
응답의 `model.syntheticData: true`와 `disclaimer`가 그것을 알리며, 결과를 저장하지
않는다. FastAPI는 운영 환경에서 합성데이터 모델을 로드하지 않는다.
자세한 것은 [demand_forecast_poc.md](demand_forecast_poc.md).

운영 환경에서 fixture를 고르면 기동에 실패한다. 수요와 발주의 기본값은
`disabled`이고, 꺼진 상태에서 호출하면 503이다. 끈 기능이 fixture로 대신
답하지 않는다.

관리자 화면은 `modelVersion`이 `fastapi-fixture-` 로 시작하면 **"개발용
fixture — 실제 AI 예측이 아닙니다"** 배지를 붙인다.

---

## 3. 실제 데이터가 없어 막힌 것

모델을 안 만든 것과는 다른 문제다. **맞힐 대상의 정답이 없다.**

### 잔반 분석
- 측정된 잔반 라벨 데이터셋: **0건**
- 정답 정의(`waste_rate = 잔반 질량 / 제공 질량`)와 수집 도구는 만들어 뒀다
- Stage 21의 실제 수집이 승인·현장 문제로 **BLOCKED** 상태 그대로다
- 합성 fixture를 "데이터셋 구축 완료"로 볼 수 없다

### 수요 예측
- 예측 대상인 **실제 급식 이용 인원**을 정답으로 쌓는 곳이 시스템에 없다
- `congestion_observations.peopleCount` 는 시점 혼잡도 지표이지 한 끼를 먹은
  사람 수가 아니다
- 잔반 제출 건수는 인증 참여자 수다
- 식권·입장 기록 같은 canonical source가 없다
- 그래서 `AIDemandRequest` 는 과거 관측치 배열을 받지 않는다

### 발주 추천
- 실제 최적화 모델도, 그것을 검증할 재고·단가·실측 소비량도 없다

## 4. 운영 전에 남은 것

기능 결함이 아니라 운영 준비 항목이다.

| 항목 | 현재 | 필요한 것 |
|---|---|---|
| SMS 발송 | `noop` 어댑터만 | 실제 SMS 사업자 연동. **현재 회원가입 E2E는 실제 문자 인증을 거치지 않는다** |
| refresh token 보관 | `sessionStorage`(JS가 읽을 수 있음) | HttpOnly + Secure + SameSite 쿠키 검토. 인증 프로토콜 변경이 필요 |
| 관리자 계정 발급 | `local`/`dev` seeder만 | 운영 발급·초기화 절차. 승격 API는 의도적으로 만들지 않았다 |
| 잔반 이미지 저장 | 로컬 디스크 어댑터 | 공유 오브젝트 스토리지(S3/R2/MinIO 등). **현재 구성은 다중 인스턴스에 적합하지 않다** |
| 호스팅 | 미정 | 같은 출처 리버스 프록시 권장. 별도 도메인이면 허용 출처를 명시한 CORS |
| 모니터링·로그 | 없음 | 수집·알림 |
| 백업·복구 | 없음 | DB 백업과 복구 절차 |
| Android 서명 | debug 서명 | 운영 keystore. **지금 만든 릴리스 APK로는 스토어 배포할 수 없다** |
| iOS | 미검증 | Windows 환경이라 빌드 자체가 불가. macOS에서 확인해야 한다 |
| 혼잡도 단계 정책 | 수집기가 `level`을 보낸다 | 인원수 → 단계 임계값이 정해진 적이 없다. 서버는 지어내지 않는다 |
| 대시보드 식사 구분 | 예측 칸이 항상 비어 있음 | 대시보드가 어느 끼니를 대표하는지 제품 결정 필요 |

## 5. 계약이 정해지지 않은 것

### 대시보드가 대표하는 끼니

`AdminDashboard` 에는 `mealType` 이 없는데 예측은 식당·날짜·끼니 단위다.
조식·중식·석식 중 무엇을 한 숫자로 보여 줄지 정해진 적이 없다.

지금은 `todayPredictedPeople` / `tomorrowPredictedPeople` 을 `null`,
`procurementPreview` 를 `[]` 로 두고 관리자 화면이 "예측 데이터 없음"과 함께
식사별 화면 링크를 보여 준다. 아무 끼니나 골라 채우면 관리자는 그 숫자가
무엇인지 모른 채 발주하게 된다.

**MVP를 막는 결함으로 보지 않는다.** 제품 결정이 나면 계약을 확정한다.

---

## 6. 이번 단계에서 닫은 것

- 관리자 웹의 식단 수정 화면이 공개 조회(`GET /api/v1/menus/{id}`)에 기대던
  것을 `GET /api/v1/admin/menus/{id}` 로 옮겼다. 같은 행을 읽지만 경로가
  나뉘어, 나중에 공개 조회가 좁아져도 관리 화면이 함께 망가지지 않는다.

---

## 7. 이 단계의 의미

**MVP 엔지니어링 완료**다. 네 구성 요소가 하나로 붙어 동작하고, 계약과 한계가
문서로 남았다.

**운영 준비 완료가 아니다.** 4절이 남아 있고, 3절이 해결되기 전에는 AI 기능을
실제 성능으로 이야기할 수 없다.
