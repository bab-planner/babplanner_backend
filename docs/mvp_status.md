# 밥플래너 MVP 현황

무엇이 실제로 되고, 무엇이 개발용 값으로 돌아가고, 무엇이 데이터가 없어서
막혀 있고, 무엇이 운영 전에 남았는지를 나눠 적는다.

이 구분이 이 문서의 전부다. 네 가지를 섞어 놓으면 "AI 기능 완성"처럼 읽히고,
그건 사실이 아니다.

---

## 1. 완료된 것

실제로 동작하고 테스트로 고정돼 있다.

### 인증과 권한
- 휴대폰 인증 → 회원가입 → 로그인 → 토큰 갱신 → 로그아웃
- BCrypt 비밀번호, refresh token 회전, 세션 저장
- 네 종류의 접근 주체: 익명 / USER / ADMIN / INTERNAL_SERVICE
- 일반 가입으로 ADMIN을 만들 수 없다. 권한 승격 API도 없다

### 사용자 기능
- 식단 조회(날짜·식사·분류·식당 필터), 상세, 영양정보, 알레르기
- 현재 혼잡도
- 잔반 인증: 이미지 업로드 → 관리자 수동 검토(승인 시 포인트 적립) → 결과 조회
- 리워드 저장과 조회
- 공지, 만족도 조사 응답, 문의/건의

### 관리자 기능
- 식단 CRUD, 공지 CRUD, 설문 등록·결과, 문의 답변
- 급식소 목록
- 대시보드(현재 혼잡도, 오늘 잔반 요약), 혼잡도 시계열, 잔반 요약·메뉴별 잔반률
- 잔반 인증 검토(목록, 사진, 승인/반려)
- 다음 영업일 점심 식수 예측(`/admin/demand-forecasts/*`)
- 관리자 웹(React) 전 화면

### 경계와 저장
- Spring ↔ FastAPI 프로세스 경계 1개(식수 예측). 혼잡도는 CCTV 수집기가 Spring에 직접 보낸다
- 혼잡도 수집 경로: 이력과 현재값을 한 트랜잭션에서 기록
- MySQL 8.4 + Flyway V1~V29
- 급식 운영일 시간대를 설정으로 분리

## 2. AI 범위와 한계

AI 서비스(FastAPI)가 하는 일은 **다음 영업일 점심 식수 예측** 하나다
(`/api/v1/admin/demand-forecasts/*`). 혼잡도는 CCTV 수집기가 Spring에 직접 보낸다.

식수 예측은 FastAPI가 저장된 모델로 계산하지만, 그 모델은 **합성데이터로 학습한
PoC**다. 응답의 `model.syntheticData: true`와 `disclaimer`가 그것을 알리며, 결과를
저장하지 않는다. FastAPI는 운영 환경에서 합성데이터 모델을 로드하지 않는다.
자세한 것은 [demand_forecast_poc.md](demand_forecast_poc.md).

잔반 인증은 AI가 아니라 관리자가 수동으로 검토한다([waste_review.md](waste_review.md)).

**제거됨(Round 4):** 일반 수요 예측(`/admin/demand-predictions`), 발주 추천
(`/admin/procurement-recommendations`), 그에 쓰이던 AI 호출과 설정은 백엔드에서
삭제했다. 관련 테이블(`demand_predictions`, `procurement_*`)은 migration을
수정하지 않아 DB에 남아 있고 코드는 사용하지 않는다(선택적 정리 대상).

---

## 3. 실제 데이터가 없어 막힌 것

모델을 안 만든 것과는 다른 문제다. **맞힐 대상의 정답이 없다.**

### 수요 예측
- 예측 대상인 **실제 급식 이용 인원**을 정답으로 쌓는 곳이 시스템에 없다
- `congestion_observations.peopleCount` 는 시점 혼잡도 지표이지 한 끼를 먹은
  사람 수가 아니다
- 잔반 제출 건수는 인증 참여자 수다
- 식권·입장 기록 같은 canonical source가 없다
- 그래서 `AIDemandRequest` 는 과거 관측치 배열을 받지 않는다

## 4. 운영 전에 남은 것

기능 결함이 아니라 운영 준비 항목이다.

| 항목 | 현재 | 필요한 것 |
|---|---|---|
| SMS 발송 | `noop` 어댑터만 | 실제 SMS 사업자 연동. **현재 회원가입 E2E는 실제 문자 인증을 거치지 않는다** |
| refresh token 보관 | `sessionStorage`(JS가 읽을 수 있음) | HttpOnly + Secure + SameSite 쿠키 검토. 인증 프로토콜 변경이 필요 |
| 관리자 계정 발급 | `local`/`dev` seeder만 | 운영 발급·초기화 절차. 승격 API는 의도적으로 만들지 않았다 |
| 잔반 이미지 저장 | 로컬 디스크 어댑터 | 공유 오브젝트 스토리지(S3/R2/MinIO 등). **현재 구성은 다중 인스턴스에 적합하지 않다** |
| 호스팅 | 미정 | 같은 출처 리버스 프록시 권장. 별도 도메인이면 허용 출처를 명시한 CORS |
| 모니터링·로그 | 없음 | 수집·알림 |
| 백업·복구 | 없음 | DB 백업과 복구 절차 |
| Android 서명 | debug 서명 | 운영 keystore. **지금 만든 릴리스 APK로는 스토어 배포할 수 없다** |
| iOS | 미검증 | Windows 환경이라 빌드 자체가 불가. macOS에서 확인해야 한다 |
| 혼잡도 단계 정책 | 수집기가 `level`을 보낸다 | 인원수 → 단계 임계값이 정해진 적이 없다. 서버는 지어내지 않는다 |

## 5. 대시보드

`GET /api/v1/admin/dashboard` 는 `{currentCongestion, wasteSummary}` 두 칸이다.
예전의 예상 식수·발주 미리보기 칸은 제거했다.

---

## 6. 이번 단계에서 닫은 것

- 관리자 웹의 식단 수정 화면이 공개 조회(`GET /api/v1/menus/{id}`)에 기대던
  것을 `GET /api/v1/admin/menus/{id}` 로 옮겼다. 같은 행을 읽지만 경로가
  나뉘어, 나중에 공개 조회가 좁아져도 관리 화면이 함께 망가지지 않는다.

---

## 7. 이 단계의 의미

**MVP 엔지니어링 완료**다. 네 구성 요소가 하나로 붙어 동작하고, 계약과 한계가
문서로 남았다.

**운영 준비 완료가 아니다.** 4절이 남아 있고, 3절이 해결되기 전에는 식수 예측을
실제 성능으로 이야기할 수 없다.
